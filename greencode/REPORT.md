# ソフトウェア省エネ化 — 調査・実証・事業化レポート

作成日: 2026年9月29日

## 要旨

- **仮説「処理を軽くすれば、今ある半導体で足りる」は、AI・データセンター・業務システムの領域では成り立つ。**
  本レポートの実測で、よくある6つの非効率を直すだけで **エネルギーを78〜97%削減（4.5〜30倍効率化）**、
  処理結果は改善前後で完全一致した。
- **データ量が増えるほど効果は拡大する。** 同じ改善でデータ量8倍のとき、差は3倍から93倍に広がった。
- ただし、**自動車・家電の部品としての半導体不足はソフトでは解決しない。** また「効率化すると需要が増える」
  （ジェボンズのパラドックス）ため、社会全体の半導体需要が減る保証はない。
- 商売としては **「省エネ」ではなく「コスト削減」として売り、CO2削減は開示用の副産物として付ける** のが
  最も通りやすい。電力不足・AI費用の急増・サステナビリティ開示の義務化という3つの追い風がある。

## 1. 市場環境の調査

### 1-1. 電力が計算の上限を決め始めている

- IEAの見通しでは、世界のデータセンター電力消費は2030年に約9,450億kWhと2024年から倍増し、
  現在の日本の総電力消費を上回る規模になる。牽引役は生成AI。[^iea]
- 日本では2030年に総電力需要の3〜5%をデータセンターが占める見込み。電力広域的運営推進機関の想定では、
  データセンター新増設分として2034年度に2024年度比で年間約440億kWhの需要増。[^japan-dc]
- **データセンターを新設しようにも、電力会社への申込みから供給開始まで早くて6年、10年かかることもある。**[^japan-dc]
  → 「チップを増やせない」以前に「電気が引けない」。**今ある設備でより多く処理する技術の価値が上がっている。**

### 1-2. ソフトの効率化は、ハードの進化より速い

- 言語モデルでは、同じ性能に必要な計算量が約8か月ごとに半減してきた（95%信頼区間 5〜14か月）。[^epoch]
  ムーアの法則（ハードの進化）を上回るペース。
- **エネルギーの大部分は「計算」ではなく「データの移動」に使われている。** 64bitの足し算が約1pJなのに対し、
  そのデータをメモリ（DRAM）から取ってくるのは1,000〜10,000倍のエネルギーがかかる。[^horowitz]
  → 省エネの主戦場は「計算を減らす」より「データを動かさない」。

### 1-3. AIの費用削減は、すでに実需がある

- 生成AI関連予算はPoC費用から本番運用費（推論コスト・運用人件費）にシフトしている。[^jp-api]
  国内AI市場支出は2029年に7兆円規模へ拡大する見通し（IDC）。[^idc]
- **用途ごとにAIモデルを使い分ける「ルーティング」が標準的な運用になりつつある。**
  簡単な問い合わせは軽量モデル、複雑な分析だけ高性能モデルに回す。[^jp-api]
- 学術研究（RouteLLM, ICLR 2025）では、高性能モデルの品質の95%を保ったまま最大85%のコスト削減。
  ただし **ベンチマークによって35〜85%と大きく変わる。**[^routellm]
- 海外では専業スタートアップが急成長している。OpenRouterは5.5%の手数料モデルで、年換算売上が
  2025年5月の500万ドルから2026年初めに約5,000万ドルへ。評価額は約13億ドル規模で交渉中と報じられている。[^routers]

### 1-4. CO2の「開示義務」が企業の購買動機になる

- サステナビリティ基準委員会（SSBJ）の基準が2025年3月に公表され、**2027年3月期から時価総額3兆円以上の
  プライム企業で義務化**。以降、1兆円以上、5,000億円以上と毎年対象が広がる。[^ssbj]
- **スコープ3（取引先を含むサプライチェーン全体の排出）のカテゴリ別開示まで求められる。**[^ssbj]
  購入したクラウドやAIサービスの排出も対象になり得るため、発注先のIT企業にも算定の要請が降りてくる。
- ソフトウェアの炭素排出を測る国際規格として **SCI（ISO/IEC 21031:2024）** がある。
  機能単位（1件の処理・1人の利用者など）あたりの排出量で評価する。2025年にはAI向けの拡張も承認された。[^sci]

### 1-5. 競合・既存の取り組み

| 領域 | 主なプレイヤー | 特徴 |
|---|---|---|
| 計測ツール | CodeCarbon, Scaphandre, Kepler（いずれも無償OSS）[^tools] | 計測はできるが、改善は利用者任せ。精度と手軽さはトレードオフ |
| AIルーティング | OpenRouter, Martian, Not Diamond（海外）[^routers] | 英語圏中心。手数料型またはカスタム学習 |
| グリーンソフトウェア支援 | NTTデータ、NTTデータMSE、NTTコムウェア[^ntt] | 大企業向け。ソフトウェアのCO2算定ルール策定も主導 |

**空白地帯**：計測ツールは無料で溢れているが、**「測って、直して、削減額を証明する」までを一気通貫で、
中堅企業に日本語で提供する**プレイヤーは少ない。

## 2. 実証実験

### 2-1. 方法

- 計測ツール `greencode`（本リポジトリ）を開発し、同じ処理の改善前後を各5回実行して中央値を比較した。
- **改善前後で出力が完全に一致することを全実験で確認済み。** 速くなっても答えが変わったら意味がないため。
- 実行環境は仮想マシン（Intel Xeon 2.1GHz, 4コア）で電力センサーに直接アクセスできないため、
  エネルギーは **CPU時間 × 8W/コア の推定値**。同一マシンでの改善前後の比は概ね成り立つが、
  絶対値は目安。実機のLinuxサーバーでは電力センサー（RAPL）の実測値に自動で切り替わる。

### 2-2. 結果

| 手法 | 内容 | エネルギー（前→後） | 削減率 | 効率 | 経過時間（前→後） |
|---|---|---|---|---|---|
| 1. アルゴリズムを変える | 重複検出 6,000件（全ペア比較 → 集合） | 3.72 J → 0.140 J | 96.2% | 26.6倍 | 0.47 s → 0.018 s |
| 2. やらない（キャッシュ） | 偏りのある3,000リクエスト（毎回計算 → 結果を記憶） | 1.98 J → 0.427 J | 78.4% | 4.6倍 | 0.26 s → 0.054 s |
| 3a. データを小さくする | 5,000万個の値（64bit → 8bit） | 5.69 J → 1.086 J | 80.9% | 5.2倍 | 0.72 s → 0.139 s |
| 3b. 並び順に読む | 8,192×8,192配列（列の順 → 行の順） | 6.38 J → 1.416 J | 77.8% | 4.5倍 | 0.80 s → 0.183 s |
| 4. 身の丈に合った道具 | 120件の処理（1件ごとに実行環境を起動 → 1回起動） | 10.56 J → 0.345 J | 96.7% | 30.6倍 | 1.34 s → 0.044 s |
| 5. まとめて処理する | 3,000行のDB書き込み（1件ずつ確定 → 一括） | 4.06 J → 0.235 J | 94.2% | 17.3倍 | 1.71 s → 0.031 s |

### 2-3. 規模が大きいほど効果が拡大する

手法1（アルゴリズム）をデータ量だけ変えて測った結果：

| データ量 | 改善前 | 改善後 | 差 |
|---|---|---|---|
| 1,500件 | 0.32 J | 0.107 J | 3.0倍 |
| 3,000件 | 0.99 J | 0.118 J | 8.4倍 |
| 6,000件 | 3.52 J | 0.125 J | 28.1倍 |
| 12,000件 | 13.26 J | 0.143 J | 92.6倍 |

**データが8倍で、差は31倍に広がった。** 小さなテストデータでは「大差ない」ように見える非効率が、
本番の大量データでは電気代・サーバー台数の大部分を食っている、という構図を数字で示せる。

### 2-4. 解釈上の注意

- **手法3a（データを小さくする）はAIでは要注意。** AIモデルの量子化（数値を小さくする手法）は、
  モデルや機種によって **逆にエネルギーが増える** 事例が報告されている（小型モデルで+25〜122%など）。[^quant]
  → 「やれば必ず減る」ではなく、**必ず改善前後を実測して確認する** 必要がある。これがそのまま計測ツールの存在理由になる。
- **手法5（まとめて処理）の実際の効果は、推定値より大きい。** 推定はCPU時間しか見ていないが、
  経過時間は55倍縮んでいる。差の大部分はディスクへの書き込み待ちで、これはCPU時間に現れない。
- **AIルーティングは本環境では実証していない。** 外部APIに接続できないため。上記の数字は公開研究の値であり、
  効果は利用内容に強く依存する（2026年の統一評価では、多くの手法の性能差が縮まることも報告されている）。[^routellm]
  顧客の実際の問い合わせログで評価してから効果を約束する必要がある。

## 3. 事業化

### 3-1. 売り方の原則

> **「省エネ」を売らない。「電気代・クラウド代・AI代の削減」を売る。CO2削減は開示資料用のおまけとして付ける。**

- 省エネは「良いこと」だが予算がつきにくい。コスト削減は財務担当が即座に判断できる。
- 省エネとコスト削減は同じ改善で同時に達成される。削減額（円）とCO2（t）を **同じ計測から両方出せる** のが強み。
- 開示義務の対象企業には、CO2の算定根拠（SCI準拠）が別の価値を持つ。

### 3-2. 商品構成（価格は仮説）

| 段階 | 商品 | 内容 | 価格の仮説 |
|---|---|---|---|
| 入口 | **計測ツール（無償公開）** | 誰でも自社の処理を測れる。見込み客の獲得 | 無料 |
| 診断 | **省エネ・コスト診断** | システム/AI利用を計測し、削減余地と見込み額をレポート | 30〜80万円／件 |
| 改善 | **改善実装（成果報酬）** | 診断で見つけた箇所を直し、削減額を実測で証明 | 実測削減額の30% × 12か月 |
| 継続 | **AI費用最適化** | 問い合わせ内容に応じてAIモデルを使い分ける仕組みの導入・運用 | 削減額の20〜30% |
| 継続 | **CO2算定・開示支援** | SCI準拠でソフトウェア／AI利用の排出量を算定 | 年額契約 |

**成果報酬を軸にするのは、顧客の「本当に下がるのか」という不安を取り除くため。**
計測ツールで改善前後を実測できるので、削減額を客観的に示せる。

### 3-3. 収益イメージ（仮説）

AI費用の最適化の例：

- 顧客のAI利用料が月100万円
- 控えめに30%削減できたとすると、月30万円の削減（年360万円）
- 削減額の30%を成果報酬とすると、**月9万円・年108万円／社**
- 顧客の手元にも年252万円が残る

効果は利用内容次第なので、**契約前に顧客のログで試算し、実測できた分だけ請求する** 形にする。

### 3-4. 狙う顧客（優先順）

1. **生成AIを本番で使い始めた中堅企業** — AI費用が急に膨らみ、削減の動機が最も強い。成果が円で見える。
2. **SSBJ対象のプライム企業のIT部門・その取引先** — 2027年3月期から段階的に開示義務。算定根拠が必要。
3. **自社サーバー／データセンターの増設ができない企業** — 電力が引けない。今ある設備で処理量を増やす価値が高い。
4. **受託開発会社・SIer** — 自社の提案に「省エネ診断」を組み込むパートナーとして。

Field&Associateの既存サービス「業務効率化・DX支援」の延長として、既存顧客（建設業・不動産業）への
提案から始めることもできる。

### 3-5. リスクと対策

| リスク | 対策 |
|---|---|
| 無料OSSがあるので計測だけでは売れない | 計測は入口と割り切り、収益は改善と継続支援で得る |
| 効果が顧客ごとに大きく違う | 契約前に顧客データで試算。成果報酬で「効かなかったら払わなくてよい」形に |
| AIの使い分けで回答品質が落ちる | 顧客ごとに品質評価用の問題セットを作り、品質を測りながら切り替える |
| 量子化などが逆効果になる場合がある | 必ず改善前後を実測。推測で効果を約束しない |
| 推定値と実電力の乖離 | 顧客の実機ではRAPL（CPU）・NVML（GPU）で実測する。報告書には必ず算出方法を明記 |
| ジェボンズのパラドックス | 顧客単位ではコスト削減が確実に効くので、事業上の問題にはならない。社会全体への効果は誇張しない |

## 4. 次のステップ

1. **GPU計測への対応**（NVIDIA NVML）— AIの推論は GPU で動くため、AI顧客を測るには必須。
2. **実案件1件での実証** — 自社か既存顧客のシステム1つで「診断 → 改善 → 削減額の実測」を通し、事例にする。
   事例が1つあるかないかで営業の難易度がまったく違う。
3. **AI使い分けの検証** — 実際の問い合わせログを入手し、品質を保ったまま何%下がるかを実測する。
4. **診断レポートの定型化** — 計測結果から顧客向けレポート（削減額・CO2・改善箇所）を自動生成する。
